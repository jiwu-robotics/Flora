# Writing Multica Agent Briefs

An Agent Brief is the durable execution specification posted to a Multica Issue
when it reaches `ready_for_agent` or `ready_for_human`. The original Issue or PR
and discussion remain context; the current Brief is the contract the assigned
agent or responsible workspace member works from. A `ready_for_human` Brief
MUST NOT cause an agent or Squad assignment.

For a PR, describe what remains to do on the existing diff. Do not ask an agent
to rebuild behavior the PR already provides.

## Principles

### Durable over precise

The item may wait while the codebase changes. Describe interfaces, types,
behavior, constraints, and evidence. Do not prescribe source file paths or line
numbers; both go stale and turn a contract into an edit script. Name a symbol,
signature, configuration shape, or externally visible contract only when it
preserves intent, then let the agent locate its current implementation.

### Behavioral over procedural

State what the system must do, not an edit sequence. Acceptance criteria must be
independently testable and cover relevant failures, boundaries, invariants, and
transitions.

### Evidence over assumptions

Include the target repository, verification revision/version, commands or
scenarios run, and observed results. Mark unresolved external facts and missing
access explicitly. Never promote inferred controller or deployment behavior to
fact.

### Scope and ownership are explicit

State dependencies, permissions, expected artifacts, and reviewer/approver.
Out-of-scope items prevent adjacent work from being silently added.

## Current version rule

Each Brief has a monotonically increasing version such as `v1`, `v2`, plus the
repository revision used for verification. Exactly one version is current.

If requirements or evidence change materially, post a new complete Brief that
says `Supersedes: Brief vN`; do not publish only a patch or silently edit quoted
history. The newest explicitly current version replaces the earlier execution
contract while prior versions remain discussion evidence. Triage notes and
dispatch checks must name the current version. A wording correction that does
not change behavior may be noted without creating a new execution version.

## Template

```markdown
> *This was generated by AI during triage.*

## Agent Brief

**Brief version:** vN
**Supersedes:** none / Brief vN-1
**Category:** bug / enhancement
**Summary:** one-line behavioral outcome
**Multica item:** routable key and canonical Multica URL
**Source request/PR:** canonical URL, when different
**Project repository:** canonical repository URL
**Verification revision:** commit, tag, or immutable version
**Reviewer:** person, team, or role responsible for acceptance

**Current behavior:**
Observed behavior and evidence. For a PR, describe the current diff and gaps.

**Desired behavior:**
Observable result, errors, boundaries, and important edge cases.

**Key interfaces:**
- `TypeName` or message/interface: compatibility contract
- `functionName()` or command: input, output, and error behavior
- Configuration/data shape: fields and invariants

**Dependencies:**
- prerequisite change, external system, or confirmed deployment input
- ordering or compatibility constraint

**Required permissions:**
- repository/workspace/Multica permissions
- external access or approval

**Verification evidence:**
- Command or scenario:
- Observed result:
- Remaining uncertainty:

**Expected artifacts:**
- code/configuration/output that must exist
- durable evidence/report that must be retained

**Acceptance criteria:**
- [ ] Specific independently testable behavior
- [ ] Relevant failure or boundary behavior
- [ ] Required evidence or compatibility invariant

**Out of scope:**
- adjacent capability not required
- unrelated cleanup or policy change
```

## Example: bug

```markdown
> *This was generated by AI during triage.*

## Agent Brief

**Brief version:** v1
**Supersedes:** none
**Category:** bug
**Summary:** Preserve complete words when truncating generated descriptions
**Multica item:** MUL-42 — https://multica.example/workspaces/acme/issues/MUL-42
**Source request/PR:** same as Multica item
**Project repository:** https://github.com/acme/tooling
**Verification revision:** 8d31c6e
**Reviewer:** Tooling maintainer

**Current behavior:** Descriptions over 1024 characters are cut at the byte
limit and may end mid-word. The focused parser scenario reproduced this at
revision `8d31c6e`.

**Desired behavior:** Truncate at the last word boundary that leaves room for
`...`; descriptions within the limit remain unchanged.

**Key interfaces:**
- `SkillMetadata.description`: remains a string capped at 1024 characters
- frontmatter description parser: preserves existing validation errors

**Dependencies:** none

**Required permissions:** repository write and CI read access

**Verification evidence:**
- Command or scenario: parser CLI with 1023-, 1024-, and 1030-character inputs
- Observed result: only the 1030-character case ended mid-word
- Remaining uncertainty: none

**Expected artifacts:** implementation plus focused boundary tests

**Acceptance criteria:**
- [ ] Inputs at or below 1024 characters are unchanged
- [ ] Longer inputs end at a word boundary with `...`
- [ ] Final output including `...` is at most 1024 characters

**Out of scope:** changing the limit or adding multiline descriptions
```

## Example: enhancement

```markdown
> *This was generated by AI during triage.*

## Agent Brief

**Brief version:** v1
**Supersedes:** none
**Category:** enhancement
**Summary:** Persist concept-level records for explicitly rejected enhancements
**Multica item:** MUL-87 — https://multica.example/workspaces/acme/issues/MUL-87
**Source request/PR:** same as Multica item
**Project repository:** https://github.com/acme/tooling
**Verification revision:** release-2026.08
**Reviewer:** Product maintainer

**Current behavior:** Rejection reasons live only in closed Issue discussions, so
later similar requests require rediscovery.

**Desired behavior:** Explicitly rejected enhancements create or update one
`.multica/out-of-scope/<concept>.md` record with durable reasoning and canonical
source links. Bugs, built features, duplicates, and temporary deferrals do not
create records.

**Key interfaces:**
- `.multica/out-of-scope/<concept>.md`: concept heading, reason, prior requests
- triage workflow: concept-similarity lookup before recommendation

**Dependencies:** maintainer rejection decision

**Required permissions:** target repository write and Multica comment/status
permissions

**Verification evidence:**
- Command or scenario: inspected closed request workflow at `release-2026.08`
- Observed result: no repository decision record existed
- Remaining uncertainty: none

**Expected artifacts:** one rule-compliant record and linked Multica conclusion

**Acceptance criteria:**
- [ ] Matching requests append to one concept record
- [ ] Every source has a canonical Multica or PR URL
- [ ] Ineligible closures never create a rejection record

**Out of scope:** automated semantic matching or reopening historical Issues
```

## Example: PR

```markdown
> *This was generated by AI during triage.*

## Agent Brief

**Brief version:** v2
**Supersedes:** Brief v1
**Category:** enhancement
**Summary:** Finish JSON error output in the contributor's existing CLI diff
**Multica item:** MUL-103 — https://multica.example/workspaces/acme/issues/MUL-103
**Source request/PR:** https://github.com/acme/tooling/pull/314
**Project repository:** https://github.com/acme/tooling
**Verification revision:** PR head 40d9a7b
**Reviewer:** CLI maintainer

**Current behavior:** The PR already implements JSON success output. Error paths
still emit human text and the diff lacks an error-case test.

**Desired behavior:** Under `--json`, success and error output are valid JSON on
stdout; without the flag, existing human output is byte-for-byte unchanged and
exit codes remain unchanged. The success payload shape already introduced by
the PR remains stable.

**Key interfaces:**
- CLI error renderer: `{ "error": string }` on stdout under `--json`
- serializer already added by the PR: must be reused

**Dependencies:** contributor diff at the named head revision

**Required permissions:** PR branch or follow-up branch write, CI read access

**Verification evidence:**
- Command or scenario: PR success path and one invalid-input path
- Observed result: success was JSON; invalid input was plain text
- Remaining uncertainty: contributor branch write permission

**Expected artifacts:** changes on the existing diff plus success/error coverage

**Acceptance criteria:**
- [ ] `--json` success and error output parse as JSON from stdout
- [ ] Exit codes match the non-JSON command
- [ ] Default output is byte-for-byte unchanged
- [ ] The PR's existing JSON success-payload shape is unchanged

**Out of scope:** adding JSON output to other commands, changing the existing
success payload, or rebuilding the PR
```

## Counterexample: unusable Brief

```markdown
## Agent Brief

**Summary:** Fix the triage bug

Change `src/triage/handler.ts` around line 150 and update the labels.
Make sure it works.
```

Reject this Brief. It has no AI disclaimer, version, category, canonical
Multica/source URL, repository, verification revision, current/desired behavior,
interfaces, evidence, dependencies, permissions, artifacts, reviewer, testable
acceptance criteria, or scope boundary. It gives brittle file/line procedure
instead of a durable behavioral contract.

For a PR, “implement the requested feature” is equally invalid when the diff
already implements part of it. The Brief must name the verified existing diff
and only the remaining acceptance gap.

## Handoff checks

Before moving an item to `ready_for_agent`, confirm:

- exactly one type label is present;
- the status key is `ready_for_agent`;
- exactly one Brief version is explicitly current;
- the Brief contains behavior, interfaces, acceptance, scope, evidence,
  dependencies, permissions, expected artifacts, and reviewer;
- repository and external inputs are named rather than guessed;
- the PR Brief describes only gaps remaining on the existing diff; and
- no equivalent Multica execution is active or queued.
