# Multica Triage

Move Multica issues and in-scope external pull requests through a small,
evidence-based triage workflow. This skill is explicit-invocation only.

## Classification and states

Every completed triage has exactly one type label and one triage status. The
issue MAY retain module, risk, source, and other non-type labels.

Type labels:

- `bug`: an existing behavior is broken, unsafe, or incorrect.
- `enhancement`: a new capability or improvement is requested.

Classify the requested behavior, not the reporter's chosen label. If one item
contains an independently actionable bug and enhancement, recommend splitting
it rather than attaching two type labels. Until the maintainer chooses the
single scope, keep it in `needs_triage`.

Positive examples:

- “Export crashes for an existing supported input” → `bug`.
- “Add JSON export where no such contract exists” → `enhancement`.
- “Fix the crash and add scheduled exports” → recommend two Issues; do not
  attach both type labels to one Issue.

Counterexample: a reporter titles an Issue “Bug: add dashboard” but describes no
broken accepted behavior. Do not copy the word “Bug” into the type label; the
request is an `enhancement` unless evidence establishes an existing dashboard
contract.

Triage statuses are custom Multica Issue Status definitions. Use the exact keys
and categories from `.multica/agents/triage-mapping.md`:

| Meaning | Status key | Category |
| --- | --- | --- |
| Needs maintainer evaluation | `needs_triage` | `backlog` |
| Waiting for actionable information | `needs_information` | `blocked` |
| Fully specified for an agent, pending explicit dispatch | `ready_for_agent` | `backlog` |
| Scoped human implementation or decision | `ready_for_human` | `todo` |
| Explicitly rejected | `wontfix` | `cancelled` |

`needs_information` is blocked until the named party or system supplies
evidence. `ready_for_agent` remains in `backlog` as an authorization gate:
`apply` records it with `--no-start`; the sole explicit dispatch transition is
to built-in `todo`. `ready_for_human` is a human work queue and MUST be
unassigned or assigned to a workspace member, never an agent or Squad. Do not
store a duplicate `triage_state` metadata property. The status is the source of
truth. Custom statuses inherit their category behavior and do not create a
second execution lifecycle or board column. After explicit dispatch, use the
normal execution lifecycle: `todo` → `in_progress` → `in_review` → `done`. A PR
that is ready for review uses `in_review`, not `ready_for_human`.

Before any classification write, read the live Issue labels and resolve both
canonical type labels by exact name and color from the current workspace label
list. After the write, the Issue MUST have exactly one mapped type label.
Preserve every non-type label. If resolution is non-unique, two type labels are
already present, or the requested scope is ambiguous, stop in `needs_triage`
instead of silently choosing. If status keys or categories do not match the
verified mapping and current Foundation lineage, stop and report configuration
drift.

## Modes

The maintainer chooses one of these modes:

- `inspect`: read-only investigation and recommendation. Do not write Multica
  state, comments, labels, metadata, or files.
- `apply`: write only the authorized classification, status, clarification,
  triage notes, and Agent Brief. Never start implementation work.
- `dispatch`: after checking the Brief, dependencies, permissions, and existing
  runs, start exactly one implementation entry point. Record all other state
  changes without starting another run.

A request that does not name a mode defaults to `inspect`; ask before applying a
recommendation or dispatching work.

## Invocation

The maintainer invokes `/multica-triage` with a natural-language request. It
can list work needing attention, inspect a specific issue or PR, apply an
approved transition, or dispatch an already-ready Brief.

Resolve identifiers through `.multica/agents/issue-tracker.md`. A routable
Multica key/UUID identifies a Multica Issue; a code-host PR/MR requires its
canonical URL or explicit repository plus number. Never guess that a bare
number refers to one surface.

Examples:

- `inspect: show issues needing triage`
- `inspect: review MUL-42`
- `apply: move MUL-42 to ready_for_agent`
- `dispatch: start the approved Brief for MUL-42`

## Discovery: what needs attention

Query Multica and present three oldest-first buckets:

3. Items in `needs_information` with new evidence from the named waiting
   party/system after the latest triage checkpoint, including reporter activity.

Show counts and one-line summaries. Mark each result `[issue]` or `[PR]`. Do
not treat a collaborator's in-flight PR as discovery work when the tracker
configuration excludes it; an explicitly named PR is always inspected. Let the
maintainer select the item; do not mutate or bulk-triage the whole queue from a
discovery request.

## Triage a specific issue or PR

1. **Gather context.** Read the complete Multica item: body, author, dates,
   labels, status, metadata, linked PRs, and execution history. Scan comment
   roots with summaries, then open only the relevant threads. Read the current
   Brief version and prior triage checkpoint. For a PR, read the diff and review
   state. Load the project domain, architecture, specification, and ADR guidance.
2. **Check history and redundancy.** Search the codebase by domain concept for
   an existing implementation, not only the request wording, and report the
   modules, interfaces, docs, and history surfaces inspected. Read every active
   `.multica/out-of-scope/*.md` record and surface a matching prior rejection.
   Do not write a rejection record for an already implemented request.
3. **Recommend.** In `inspect` mode, state the type, status, reasoning, relevant
   codebase facts, and unresolved questions. Wait for maintainer direction
   before `apply` or `dispatch`.
4. **Verify.** For a bug, reproduce the reporter's steps or explain why the
   evidence is insufficient. A confirmed bug must identify the responsible code
   path or interface boundary, not merely repeat the symptom. For a PR, inspect
   the diff and run the applicable project checks. Record the exact evidence and
   result: confirmed, failed, or insufficient detail.
5. **Clarify when needed.** Use the optional `grilling` and
   `domain-modeling` capabilities when available. If unavailable, ask one
   focused round at a time so later questions incorporate earlier answers.
   Establish observable behavior, affected interfaces, constraints, acceptance
   criteria, and ownership without inventing domain facts. When clarification
   resolves a durable term or architectural decision, update the repository's
   existing domain/ADR owner through its governed workflow; do not create a
   second documentation convention from triage.
6. **Apply the outcome.**
   - `ready_for_agent`: write the complete Agent Brief.
   - `ready_for_human`: write the same Brief structure and explain why the work
     requires human judgment, external access, design decisions, or manual
     testing.
   - `needs_information`: write the triage notes and preserve confirmed facts.
   - `wontfix`: for an explicitly rejected enhancement, write or update the
     matching `.multica/out-of-scope/<concept>.md` record, link it in the Multica
     comment, and set the terminal status. For an already implemented request,
     point to the implementation and do not write an out-of-scope record. For a
     rejected bug claim, explain the evidence-based decision in Multica and do
     not write an enhancement rejection record.
   - `needs_triage`: apply the status when evaluation is incomplete.


## Quick maintainer override

When the maintainer explicitly supplies the type or target state, trust that
decision and skip optional grilling. Before `apply`, state the exact label,
status, comment, and terminal effects; then use recording-only writes. A
`ready_for_agent` override still requires a current complete Brief before
dispatch. If the Brief is absent, record the maintainer's classification but
leave the handoff incomplete and ask whether to create the Brief; never start
implementation from a bare status override.

## State transitions and recovery

An untriaged item normally moves to `needs_triage`, then to
`needs_information`, `ready_for_agent`, `ready_for_human`, or `wontfix`. When
the named waiting party/system supplies the requested evidence, return it to
`needs_triage` and re-evaluate. The maintainer MAY override a transition. If a
transition is unusual for the recorded evidence, flag it and obtain maintainer
confirmation before writing; then record the reason.

Every `needs_information` write is a durable checkpoint containing the
confirmed facts and evidence, verification revision/result, unresolved
questions, waiting party or system, current Brief version/state, linked PR when
applicable, and the next decision. End the run after posting that checkpoint;
do not continue implementation while waiting.

On resume, read the Issue, current labels/status, comment-root summaries,
relevant checkpoint thread, current Brief, linked PR, repository revision, and
execution history. Compare reporter activity with the checkpoint, mark answered
questions resolved, preserve still-valid facts, and continue from the first
unresolved decision. Do not re-ask answered questions, rewrite a settled Brief
as a new one, or dispatch an equivalent active/queued run.

Positive recovery example: the checkpoint asks for controller version and a
reproduction command; the reporter supplies only the version. The next run
records the version as established and asks only for the command.

Counterexample: posting “please provide more information,” ignoring the prior
answer, and asking for both fields again. That loses durable context and violates
the no-repeat recovery rule.

## Needs-info note template

```markdown
> *This was generated by AI during triage.*

## Triage Notes

**Checkpoint:** YYYY-MM-DD / verification revision

**What we've established so far:**

- confirmed fact with evidence
- confirmed constraint or decision

**Verification:** command/scenario and observed result

**Current Brief:** none / version and status

**What we still need from you:**

- one specific, actionable question
- one specific, actionable question

**Waiting on:** reporter / maintainer / external system

**Next decision:** one concrete decision after the answer arrives
```

Questions MUST be specific and actionable. Preserve all facts resolved during
clarification so a later run can resume without repeating the conversation.

## Acceptance invariants

Before considering the first release or an update usable, exercise and confirm:

- **Type mutual exclusion:** classification readback contains exactly one of the
  mapped `bug`/`enhancement` UUIDs and preserves other labels.
- **Needs-info recovery:** a second run consumes the checkpoint, recognizes new
  evidence from the named waiting party/system, and does not repeat answered
  questions.
- **Brief completeness:** bug, enhancement, and PR Briefs name one current
  version and include repository, verification evidence, dependencies,
  permissions, artifacts, reviewer, acceptance, and scope.
- **Rejection correctness:** only explicitly rejected enhancements create or
  update active concept records with complete source URLs; ineligible closures
  and withdrawn records do not poison prior-rejection matching.
- **PR triage:** the Brief describes gaps remaining in the existing diff, and a
  review-ready PR uses `in_review`.
- **No accidental start:** every `apply` status/assignment/update uses
  `--no-start`, and readback shows no new run.
- **No duplicate dispatch:** an active or queued equivalent run blocks a second
  start; a fresh dispatch uses exactly one start entry point.
- **Truthful partial failure:** the operation ledger and readback report actual
  labels, status, comments, repository records, and run state after a failed
  write.
- **Runtime support files:** `MULTICA.md`, `AGENT-BRIEF.md`,
  `OUT-OF-SCOPE.md`, project `.multica/agents/` configuration, and
  `agents/openai.yaml` are readable through the installed/bound skill.
